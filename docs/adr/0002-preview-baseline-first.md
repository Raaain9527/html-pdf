# ADR 0002: 分阶段落地 + 投影缩放/生命周期决策

**日期**：2026-08-05
**状态**：已决定（grilling 会话确认）

## 上下文

ADR 0001 定了目标架构（流式投影）。用户在此基础上补了三条决策，并明确**先跑通当前流程作为基线，再动工 ADR 0001**。

## 决策

### 1. 分阶段落地（process）
- **Phase 1（现在）**：验证/修复当前 srcdoc iframe 流程，使其**端到端跑通**（预览能看、导出正确），作为基线
- **Phase 2**：基线通过后，再按 ADR 0001 实现流式投影
- 理由：先有一个可工作的当前实现兜底，避免一步跨到重架构后发现回归无从比对

### 2. 投影缩放模型（Phase 2）
- 默认 **fit 适配**（整帧缩到面板宽，看全貌）
- 叠加 **图像级缩放**（放大缩小帧图像）
- 图像缩放时滚动语义切换为图像平移（与页面滚轮的冲突由模式/修饰键管理）
- **实现补充（2026-08-06）**：加入**断点感知自动适配视口**——打开页面后 daemon 测量内容宽度，若页面远窄于视口则自动把视口调到内容宽+边距让页面铺满；若适配后页面变成全宽（命中自身响应式断点），抬升视口直到布局稳定（避免两列塌成一列）。用户手动改过视口后不再自动适配。

### 3. daemon 生命周期（Phase 2）
- **懒加载**：首次预览时才拉起 daemon + Chrome，**加载中明确提示用户**
- 首次加载后**常驻**（不再回收，后续预览秒开）
- 提供 **"关闭 Node" 手动开关**：用户可自行停掉 daemon，释放内存

## 理由

- fit 保证打开预览立刻有整体认知，图像缩放补细节，二者组合覆盖"先看全貌、再看细节"的阅读路径
- 懒加载避免常驻 200MB 白耗；首次后常驻换取后续秒开；手动关闭把控制权交给用户

## 后果

- Phase 1 期间预览的坍塌/高度问题仍存在，**属于已知基线缺陷**，不作为阻挡 Phase 1 验收的硬伤（以"流程能跑通"为验收标准）
- Phase 2 的 daemon 内存 ≈200MB，靠懒加载 + 手动关闭缓解
- 缩放三模式需要额外的工具栏 UI（fit/1:1/zoom + 模式切换）

## 备选方案

- 直接上 Phase 2（否掉）：无基线可比对，回归风险高
- daemon 应用启动即拉（否掉）：预览未用时也耗 200MB
- 仅 fit 无图像缩放（否掉）：细节无法检查，长页面无用
