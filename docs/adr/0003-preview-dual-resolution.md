# ADR 0003: 预览双分辨率混合（运动流畅 + 静止清晰）

**日期**：2026-08-06
**状态**：已决定（grilling 会话确认）

## 上下文

Phase 2 预览用 `page.screenshot()` at DSF=2（3360×1800）按交互防抖截图。实测（`html-pdf` 简历）：

- DSF=2 截图耗时 83ms（中位）→ 理论上限 ~12fps
- 80ms 防抖 + 串行截图 → **滚动/拖拽全程 0 帧（画面冻结），松手后才出一帧**

"清晰（DSF 2）" 与 "流畅（高帧率）" 直接冲突。用户确认分层原则：

- **运动时**（滚动/拖拽）：人眼看不清细节 → 低分辨率 + 流畅优先
- **静止时**（停下看/放大检查）：清晰优先

## 决策

**双通道混合**：同一个 DSF=2 视口下同时维护两套帧源

| 通道 | 时机 | 分辨率 | 机制 |
|------|------|--------|------|
| 实时帧 | 滚动/拖拽期间 | 视口 CSS 分辨率（DSF=2 视口下 screencast 仍按 CSS 输出，如 980×900），~15-30fps | `Page.startScreencast` 连续推帧 |
| 高清帧 | 静止 ~250ms 后 | DSF=2（如 1960×1800） | `page.screenshot()` 替换实时帧（"渐进清晰"） |

前端画布缓冲按高清帧分辨率（视口×DSF），实时帧拉伸填满（运动时略软可接受）；高清帧到达自然覆盖 → 画面"唰"地变清晰。

## 理由

- screencast 天然无视 DSF、按 CSS 视口输出 → 同一 DSF=2 视口下两通道无需切换 DSF，实现干净
- 运动模糊掩盖实时帧的低分辨率；静止后高清帧补上细节
- 消除"滚动冻结"，换来流畅手感

## 后果

**正面**
- 滚动/拖拽有实时反馈（不再冻结）
- 静止后自动变清晰（标准预览工具手感）

**负面**
- 双通道复杂度：daemon 维护 screencast 推帧 + 高清截图两套逻辑 + ack
- 放大到高倍时实时帧软（静止后高清帧救场）——用户已接受
- **需验证**：screencast 的 ack 与鼠标 Input 派发是否竞争（Phase 2 曾因 `page.screenshot()` 与 mouseup 并发导致点击变拖选）。若竞争则需把 CDP 操作排队

## 备选方案

- 连续串行 DSF=2 截图（skip-if-in-flight）：滚动 ~12fps，简单但不顺滑 —— 否掉
- DSF=1 实时 + DSF=2 静止：~27fps 实时，但每次捕获要切换 DSF，开销与复杂度高 —— 否掉
